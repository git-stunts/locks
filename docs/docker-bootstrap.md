# Docker bootstrap implementation status

Issue #93 is incomplete. The ordinary runner now refuses a missing or stale image instead of starting an unguarded build. It creates workers from the verified image ID with `--pull never`. A matching existing image remains the supported local path. Four orchestration cases have passed inside the guarded Docker worker. These cases mock Docker calls; real fresh provisioning remains unverified.

`scripts/docker-ci.py` is a disabled provisioning prototype for disposable GitHub-hosted Linux runners. Its entry point refuses execution before any privileged operation. It is not wired into CI and is not an approved setup command. Do not remove the refusal until the requirements below have executable evidence.

The proposed boundary is a private Docker daemon, a private socket and runtime directory, a 19 GiB loop filesystem, and a cgroup v2 slice with two CPUs, 4 GiB memory, no swap, and a process limit. The existing offline test worker would run in that daemon. The provider must retain bounded receipts, stop all owned processes, unmount its own filesystem, and remove only its own resources. It must preserve every unrelated daemon, container, volume, and cache.

Docker's `data-root` alone is insufficient with the containerd image store: images and snapshots can be stored outside that directory. The draft selects classic `overlay2`, disables the containerd snapshotter, omits any shared containerd endpoint, and checks the private daemon's reported storage driver and root. These are configuration requirements, not proof that all writes stay inside the quota. See [Docker daemon storage](https://docs.docker.com/engine/daemon/) and [daemon options](https://docs.docker.com/reference/cli/dockerd/).

The quota check reads the kernel loop device's `backing_file` attribute and compares it with the owned image path. The [Linux loop driver](https://github.com/torvalds/linux/blob/master/drivers/block/loop.c) exposes the backing file path through this attribute. This check does not establish daemon or workload membership in the owned cgroup.

The build's RUN processes also need explicit membership in the owned cgroup. Docker documents `--cgroup-parent` for [build commands](https://docs.docker.com/reference/cli/docker/buildx/build/). Membership must be observed during a real build; a command-line option or configured memory limit alone is not evidence that descendants obey it.

If receipt export fails, cleanup still attempts to unmount the owned filesystem and remove its unit. It preserves the control directory and unexported logs for recovery. If unmounting fails, it preserves the mounted data and unit. Cleanup uses recursive unmounting, then checks the kernel mount table for remaining mounts at or below the owned path. Ten synthetic cleanup cases cover receipt and log collisions, copy failures, nested mounts, failed unmounting, and remaining or unreadable mount state. A separate read-only check distinguishes the test worker's real tmpfs mount from an unmounted directory. Real privileged teardown remains unverified. See the [util-linux unmount manual](https://github.com/util-linux/util-linux/blob/master/sys-utils/umount.8.adoc) for recursive unmount behavior.

`scripts/docker-admission.py` supplies a protected receipt primitive for the remaining inner-admission gap. It checks root ownership, sticky-directory protection, no-follow opens, regular single-link files, bounded size, run identity, capacity, and freshness. Forty tests cover these rules, including the existing worker's actual directory metadata and rejection of a receipt owned by UID 1000. Successful root publication uses synthetic ownership facts in these tests. Both runners now use this primitive. The host publishes and refreshes proof only after a live boundary check, through isolated Python running its trusted host copy as root inside the owned container. It does not execute a worker-writable script as root. The inner runner requires a matching fresh receipt on every quota measurement. Initial publication failure prevents child launch; refresh failure cancels the worker. A separate live check now verifies actual root publication in the existing bounded container, refusal of worker writes/unlinks/chmod/replacement, expiry without refresh, and successful root refresh. It supplies a synthetic capacity admission; it does not prove the private daemon or a real quota filesystem.

Run the live receipt check with `python3 scripts/test-admission-live.py` under the workstation heavy-work and git-locks worker reservations. It reuses the guarded runner, gives the coordinator a 60-second deadline, and stops remote work before terminating the local launcher on failure. Only the receipt publisher runs as root in the existing container; the probe runs as UID 1000.

Work required before enabling the prototype:

- Verify the new setup ordering and ownership tests. Formatting now uses the controlled command path after cgroup checks. Unit ownership is recorded before activation, mount state is checked after errors, and refusal cleanup leaves pre-existing resources untouched. These paths still need execution evidence in the privileged setup environment.
- Prove monitor death stops the actual daemon, build processes, and test processes. A separate heartbeat watchdog is now implemented, with nonprivileged process-group fault tests for shutdown, stalled monitoring, watchdog death, and abrupt monitor death. These tests do not establish that real Docker descendants occupy the enforced cgroup. Killing only a client remains insufficient.
- Integrate the intentionally small quota filesystem with both host and in-container free-space guards. Both runners keep the ordinary 50 GiB floor and now have a conditional private-bootstrap path. The provider now checks root ownership, protected path types, backing-image size and link count, the kernel loop-device backing path, filesystem capacity, and free reserve. Synthetic kernel-fact tests cover acceptance and refusal; they do not prove a real mount. After successful resource checks, the provider also publishes a short-lived health record with monitor and watchdog PIDs, start times, and their parent relationship. Its verifier rejects stale records, unsafe file ownership, changed process identities, and unrelated watchdogs. A separate admission function combines quota identity and monitor health with daemon storage settings, CPU/memory/swap/process limits, physical backing space, and the daemon and worker process identities and cgroup membership. The host runner uses this check before admitting a small backing filesystem and repeats it while the command runs, rejecting changed quota or process identities. Only after host admission does it publish a protected receipt and pass the capacity and run identity to the inner runner. The inner runner checks receipt freshness, actual root capacity, and free reserve. A numeric capacity alone is refused; direct invocation with an unproved run identity is refused before child launch. The ordinary path keeps its 50 GiB floor. These paths still need privileged execution evidence. Any exception must keep continuous checks on the physical backing disk; an environment-only bypass is not acceptable.
- Audit every containerd, BuildKit, daemon, temporary, client, runtime, and log path. Include host-side receipts and setup logs in aggregate limits. Preserve earlier evidence and stop before a log reserve is consumed.
- Prove cleanup after cancellation, timeout, exhausted quota, low physical space, malformed monitoring data, daemon failure, and failed export. Preserve mounted recovery data if process death or unmounting cannot be verified.
- Run a real guarded fresh setup and cached-image reuse. Record resource peaks, image identity, process/cgroup membership, quota identity, cancellation results, and retained usage. Only then update CI to use the provider and verify a fresh hosted run.

The implementation must keep one coherent issue/PR boundary: a cached-only refusal is useful preparation, but it does not complete fresh provisioning or justify merging a change that breaks fresh CI.
