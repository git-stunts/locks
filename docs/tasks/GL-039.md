## 1. Background Context

A record OID identifies content. It is not automatically a monotonic fence or permission to write a protected service.

## 2. The Question

Can the selected resource reject stale writes under the proposed identity and publication protocol?

## 2b. What decision waits on it

Define a resource boundary that can reject stale owners and test whether the proposed identity protocol is sufficient.

## 2c. What would settle it

- [ ] Name the protected write operation and its authoritative check.
- [ ] Analyze the race between validation and the write.
- [ ] Define replay, delayed requests, renewal, and replacement behavior.
- [ ] Record which guarantees belong to the server rather than the cooperative client.

Golden: Model an authorized write at the resource.
Edges: Delay an old owner until after replacement.
Known failure modes: Require the resource to reject the stale write.
Fuzz and stress: Use isolated bounded server fixtures only after design acceptance.

## 2d. Aperture

A sample hook does not prove enforcement for arbitrary files or services.

## 2e. Possible answers and what each implies

Use resource-enforced monotonic fencing; define a safe compare-and-write operation; or keep the claim advisory.
