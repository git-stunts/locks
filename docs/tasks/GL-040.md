## 1. Background Context

Semaphore capacity meters holders. A TTL recipe does not by itself establish all advertised sliding-window rate guarantees.

## 2. The Question

Under which assumptions does a TTL-slot recipe enforce a specific sliding-window admission bound?

## 2b. What decision waits on it

Prove or reject a precise admission-rate contract before adding auto, burn, or next-free interfaces.

## 2c. What would settle it

- [ ] Define window boundaries, clock assumptions, release policy, and admission identity.
- [ ] Test early release, retries, replacement, delayed publication, and clock movement.
- [ ] Keep ordinary semaphore capacity claims separate from rate claims.
- [ ] Create an implementation task only for a demonstrated contract.

Golden: Compare admitted timestamps with an independent window oracle.
Edges: Test exact boundaries and duplicate job reuse.
Known failure modes: A refusal or retry must not accidentally reset the intended budget.
Fuzz and stress: Use a finite simulated clock corpus and a bounded live pilot.

## 2d. Aperture

One small demonstration cannot prove all window and retry schedules.

## 2e. Possible answers and what each implies

Document a limited recipe if proven; add a separate rate protocol if justified; otherwise reject the rate claim.
